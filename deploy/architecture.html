Skills Evaluation on POCDAPP314
one server, one ingress, a hostname per app.

How the Skills Evaluation & Enablement application is hosted, how nginx exposes it under its own domain name and certificate, and how users reach it. The same pattern is intended to carry the next applications, starting with dq-studio, by adding one configuration file each.

1. How a user reaches the application

config in deploy/nginx/
The single most important line in this diagram is the middle arrow. The app container publishes on 127.0.0.1:8001 and nowhere else, so nginx is the only route in. Publishing it as 8001:8000 instead would bind 0.0.0.0 and expose the application over plain HTTP on 10.21.12.62:8001, bypassing TLS, the redirect and every security header. The binding is written explicitly in docker-compose.yml for that reason.
The control plane is the more dangerous half. Portainer mounts the Docker socket, which cannot be read-only because creating containers is its whole function. Anyone who authenticates to that UI can start a container that mounts the host filesystem. Its admin password is effectively root on POCDAPP314, which is why it is published on loopback only, reached through nginx, and why its vhost should carry an IP allow-list.

3. Two ways users access this, both supported

verified: offline path makes zero network calls
Path A

Portable file, offline

A lead opens the HTML file straight from disk or a shared drive. Everything stays in browser memory and an evaluation is saved by downloading a JSON file. No login, no server, no network access of any kind.

no loginworks air-gapped

This is the existing distribution and it is unchanged. The apps detect file:// and skip the server probe entirely, so the server-only buttons never appear.

Path B

Served, with shared storage

A lead browses to the application hostname over HTTPS, signs in, and saves evaluations to Postgres. The team summary can load every stored evaluation in one action instead of picking files.

login requiredshared pool

Leads only. Any authenticated lead can read and write any evaluation; consultants do not have accounts. Every write records who made it.

Why both. The offline file is what people already use, and the deployment is additive rather than a replacement. The same HTML serves both worlds: it probes the API once when served over HTTP or HTTPS, and reveals the save and open controls only if that probe answers.

The port column is the loopback port each app publishes on. It is never reachable from the network. Register a port here before using it.

Why one IP serves many names

nginx reads the Host header, and during the TLS handshake the client's SNI extension, to decide which application a request belongs to. Each app therefore gets its own domain name and its own certificate while sharing 10.21.12.62.

Per-app IP addresses remain available: request additional addresses, add them as secondary addresses on the interface, and change each vhost's listen directive. That would let firewall rules target an app by destination address.

It would not add isolation. It is still one nginx, one kernel, one host and one Docker daemon. If isolation is the real requirement, the answer is separate hosts.

decision: shared IP

5. Security boundaries

5 boundaries

1. Network

Only 443 and 80 are exposed, and 80 answers only with a redirect. The application port is bound to loopback, and Postgres publishes nothing at all.

2. Transport

TLS 1.2 and 1.3, terminated at nginx with an internal CA certificate. HSTS is set for one year. The session cookie is marked Secure via COOKIE_SECURE=true, which is mandatory once TLS is in front.

3. Identity

Argon2 password hashes, server-side sessions holding opaque random tokens, and an HttpOnly, SameSite=Strict cookie. The first admin account is created at startup from a mandatory environment variable with no default.

4. Administration

Portainer is published on loopback and reached only through nginx on its own hostname, with baseline headers but deliberately not the application CSP, which would break its UI. Its image is pinned rather than tracking latest. An IP allow-list for the administrator subnet is present in the vhost but commented, and setting it is the single highest-value control here.

5. Data

Writes are append-only and there is no delete endpoint, so a mistaken save cannot silently destroy a completed review. Every row records who wrote it.

Known weaknesses, stated plainly

accepted trade-off

The content security policy allows 'unsafe-inline' for scripts. Both apps are single-file HTML with one large inline script; a strict policy breaks them outright. Removing it means per-deploy script hashes or extracting the script to a served file, and the latter ends the portable-single-file property the whole design protects. Revisit before anything internet-facing.

decision needed

No login throttling or account lockout. Brute-force protection was scoped out, not overlooked.

open action

No backup schedule and no container log rotation. The first risks data loss, the second will eventually fill the disk.

accepted consequence

The admin plane shares the app's ingress. A broken nginx config removes the management path at the moment you most need it. The mitigation is process, not architecture: never reload nginx without a clean nginx -t, and keep SSH working as the out-of-band route. An SSH local forward to 127.0.0.1:9000 reaches Portainer with nginx entirely out of the picture.

out of scope

Portainer's own users and roles are not designed. This assumes a small number of administrators sharing appropriate access. If it becomes the control plane for apps with different owners, that access model needs work.

single point of failure

One host, no redundancy. Acceptable for a proof of concept; not for a service anyone depends on.

gate before real data

Personal data review

Once real evaluations are loaded, this database becomes a shared system of record for named-employee performance data on EU staff, including performance classification and promotion recommendation. The Data Privacy Officer should review the design before real evaluations are loaded, and database backups inherit the same handling requirements. Running the proof of concept against the bundled synthetic test data raises none of this.

6. Rollout sequence

none of this has run yet
Prepare
Confirm the DNS zone and the nginx version on the box. Request the A record and the certificate. Confirm the lab can pull container images, or side-load them.
Deploy
Install Portainer first - it cannot deploy itself - and create its admin account immediately. Register the app as a git-backed stack with its environment variables, then prove 127.0.0.1:8001 answers while 10.21.12.62:8001 does not. Install the certificates and nginx files, then nginx -t before any reload.
Verify
HTTPS serves both apps, HTTP redirects, the bare IP returns 404, no certificate warning on a managed machine, and sign-in plus save plus open-from-server round trips. Then reboot the host and confirm everything returns.
Never reload nginx without a clean nginx -t. A reload with a broken configuration keeps the previous one running, but a restart would take down every application on the host, not just this one. That is the cost of a shared ingress and it is worth knowing before the second app is added.

7. Adding the next application

one file, one DNS record

This is the reason for the shared-ingress shape. Onboarding dq-studio touches nothing belonging to the Skills Evaluation app. Only steps 3 and 5 below need shell access - the application itself is deployed entirely through Portainer, so the person deploying need not be the person with sudo.

  1. Allocate the next loopback port in the registry, 8002.
  2. Request an A record for dq-studio.<zone> pointing at 10.21.12.62, and a certificate for that hostname.
  3. Copy skills-eval.conf to dq-studio.conf and change four things: the server_name, both certificate paths, the upstream name and port, and the log paths.
  4. Register a second git-backed stack in Portainer for that app, publishing on 127.0.0.1:8002, with its own environment variables.
  5. Validate and reload: nginx -t, then systemctl reload nginx. The reload is graceful and does not drop existing connections.
