# Skills Evaluation v7.0 - handover

## Executive summary

The Skills Evaluation tool has been extended from two standalone HTML files into a
deployable service: **FastAPI + Postgres in Docker Compose, with basic authentication for
leads and shared server-side storage of evaluations.**

The change is **additive**. Both single-file apps still work exactly as before when opened
from disk, with no network calls and no behaviour change. The server is an optional layer
that the same HTML detects at runtime.

**Status: code complete, not yet proven to run.** The machine this was developed on has
neither Docker nor Postgres, so the container build, `docker compose up`, and all 27
automated tests are **unexecuted**. Everything that could be verified without a database has
been. The first task for whoever picks this up is to run the test suite against a real
Postgres - see "Next steps".

Nothing has been committed. All changes are in the working tree of
`~/repos/syniti-consultant-eval`.

## What was built

| Area | Detail |
|---|---|
| API | `server/app.py` - health, login/logout/me, reference data, evaluations save/list/get/all |
| Auth | `server/auth.py` - argon2 password hashes, server-side sessions (opaque tokens), HttpOnly + SameSite=Strict cookie, first admin created from a mandatory env var |
| Storage | `db/schema.sql` - three tables (`users`, `sessions`, `evaluations`). Evaluations stored as JSONB exactly as the tool emits them |
| Container | `Dockerfile` (non-root, healthcheck on an unauthenticated `/api/health`), `docker-compose.yml` (app + Postgres, healthchecked, named volume), `.env.example` |
| Frontend | Both apps gained runtime feature detection plus server-only controls. The eval app gained a real restore path (`srvApplyDoc`) |
| Build | The team summary app is now **generated** from `build/template-team.html`; `build.py` emits both apps |
| Shared code | `refdata.py` - one loader for `data/*.json`, used by the builder and by `GET /api/reference` |
| Tests | `tests/` - 27 tests including an end-to-end check against `test-data/EXPECTED_RESULTS.md` |
| Seed | `python -m server.seed` loads the 34 synthetic evaluations. Never runs automatically |

### Design decisions

Fourteen decisions were agreed before any code was written and are recorded in **`CLAUDE.md`**,
with `DEC-7` and `DEC-8` in `issues.md` pointing at them. Read `CLAUDE.md` first. The
important ones:

- **Leads only, shared pool.** Any authenticated lead can read and write any evaluation.
  Consultants do not log in. `created_by` is recorded for audit, not access control.
- **No scoring logic on the server.** All maths stays in the apps' JavaScript. The server
  stores and returns documents verbatim.
- **Append-only.** Every save inserts a row; reads return the newest per consultant and date.
  There is no update and no delete.
- **`data/*.json` remains the single source of truth** for the competency matrix and learning
  catalog.

### Side benefits

- **LIM-5 is closed.** The team app's hand-maintained copy of the competency matrix is gone;
  both apps are built from `data/competencies.json`.
- **Two pre-existing bugs fixed** in `build.py`: no explicit file encoding, and newline
  handling that made the build produce different bytes on Windows than on Linux. The second
  one mattered because the container builds on Linux.

## What was verified

- Both apps' JavaScript parses cleanly; each embeds 78 competencies across 13 areas.
- The team app extraction is behaviour-preserving: its old embedded matrix parsed to data
  identical to `data/competencies.json`, and the rebuild changed exactly one line.
- The eval app diff is **173 insertions, 0 deletions** - provably additive.
- Opened from `file://` the tool issues **zero network requests** and the server controls stay
  hidden. The offline distribution is unaffected.
- The restore path was executed live in a browser: every field, the rating buttons, N/A flags,
  the learning plan and the provider filter all repopulate, and re-exporting reproduces the
  same ratings.
- The build is idempotent, and the em dash guard was confirmed to fail the build.
- All Python compiles; all 27 tests collect with no import errors.

## What was NOT verified

- The Docker image has never been built.
- `docker compose up` has never been run.
- **All 27 tests are unexecuted.** They skip without `TEST_DATABASE_URL`, and skipping is not
  passing.
- No SQL has ever reached a Postgres server. Wiring was confirmed only by pointing the app at
  a closed port and observing it fail at the connection stage.

## Next steps before completion

**1. Run the test suite against a real Postgres.** This is the gate; everything else is
secondary.

    docker run --rm -e POSTGRES_PASSWORD=test -p 5433:5432 -d postgres:16-alpine
    set TEST_DATABASE_URL=postgresql://postgres:test@localhost:5433/postgres
    python -m pytest tests -q

Expect 27 passed. Pay particular attention to two things that have never run: the
`DISTINCT ON (consultant, eval_date)` latest-revision query, and the
`make_interval(secs => %s)` session-expiry call.

**2. Bring the stack up and smoke-test it.**

    copy .env.example .env      # fill in POSTGRES_PASSWORD and ADMIN_PASSWORD
    docker compose up --build

Then check: `/` serves the eval app, `/team` serves the summary, the server buttons appear,
sign-in works, save then reload then open-from-server returns the same evaluation, and
`python -m server.seed` followed by the team app's "Load from server" reproduces the KPIs in
`test-data/EXPECTED_RESULTS.md`.

**3. Regression-check the offline files.** Open both files in `tool/` directly from disk and
confirm nothing changed for an offline user. This was verified programmatically but deserves
a human click-through, since it is the distribution most people actually use.

**4. Decide on the deliberate omissions.** None of these are bugs; they were scoped out and
need a decision:

- No login throttling or account lockout.
- No delete or soft-delete. A mistaken save can currently only be removed with `psql`.
- No backup or restore runbook for the `pgdata` volume.
- Single-sign-on (Entra ID) was considered and deferred; it is the right destination if this
  becomes the system of record.

**5. Commit and raise a PR.** Nothing is committed yet. `gh` was not available on the
development machine.

## Blockers before any real data

Two hard gates. Both are documented in `CLAUDE.md`.

1. **TLS.** The default compose serves plain HTTP, so session cookies are not `Secure`. This
   must sit behind TLS with `COOKIE_SECURE=true` before it holds a real evaluation.
2. **Data privacy review.** The database becomes a shared system of record for named-employee
   performance data on EU staff, including performance classification and promotion
   recommendation. The **Data Privacy Officer should review the design before real evaluations
   are loaded.** Developing and testing against `test-data/` is fine - that data is synthetic.
